# Changelog

All notable changes are recorded here. Versions follow [Semantic Versioning](https://semver.org/).

## [1.0.2] — 2026-10-13

Findings filed in the right area more often, and fixes checked by breaking them.

- **Fixes are checked by breaking them.** After `/flight-check:fix` or `/flight-check:remediate` fixes a problem and adds a test, it undoes each part of the fix in turn and runs the tests, which must fail every time. A break that survives with every test green shows that the tests miss the real path (for example, they call a function directly but never the line that wires it in), so a test that covers it is added. The fix is restored after each break, and the result is reported in plain words and recorded with the fix.
- **Findings land in the right area more often.** Every checking agent and the verifier now share one guide for choosing a finding's area by the harm it describes, not by the file it was found in, with the pairs most often confused (authentication or authorization; application security, data protection, or privacy; reliability, operational readiness, or production readiness; documentation or the gap itself). The verifier, which sees all findings together, can move a finding to another area with a new optional `domain` field in its verdict. The move changes the finding's `rule` prefix, is recorded as `verification.original_domain`, and is shown in the report.
- **Measured once, before the logs change below.** A re-run of the benchmark application whose misses prompted this change found every seeded issue at the right place, as before, and filed 93% of them in the expected area (89% before; must-find issues 96%, before 91%), with the same decoy false-alarm rate. This is one run on the application the misses came from, not a held-out evaluation.
- **No more overlap between two checks on logs.** `APPSEC-ERROR-DISCLOSURE` now covers only what error responses show users and clients (stack traces, internal details, secrets). Credentials, tokens, and personal data written to logs or error trackers belong to `DATA-SENSITIVE-HANDLING` (data protection). Before, both checks claimed sensitive data in logs, so the same problem could be filed in either area.
- **Benchmark runner** (development only): headless runs no longer stop at the audit's spending-limit question; the runner's `--budget` is the hard cap.

## [1.0.1] — 2026-10-13

Easier first steps for new users.

- **Getting started.** New `/flight-check:start` explains what Flight Check does, what it costs, where the project stands, and the first steps. Claude starts it on its own when the user asks how to use Flight Check, because the audit itself stays hidden from Claude so it never spends money unasked.
- **Fewer prompts during an audit.** The audit may write its own working files (`run.json`, `summary.json`, agent replies) in `.flight-check/runs/` without asking. It still cannot edit project files, and the lint rejects any other pre-approved write.
- **A first result that does not discourage.** When a first audit is not READY, Flight Check says first that this is normal for a first check, and why, before the next steps. After a first audit, it mentions once that questions can be asked anytime and that watch mode is available.
- **Quick start** at the top of the README.

## [1.0.0] — 2026-10-13

First release. 1.0.0 keeps everything in the release candidate below (1.0.0-rc.1) and adds project state, so Flight Check remembers the project between audits: its profile, requirements, decisions, risks, legal review queue, finding history, and what changed. Upgrading from the release candidate changes some files in `.flight-check/` on the first command that records something; see `docs/upgrading-from-rc.md`, including how to go back. During development this version was called 1.5; records from that time (`docs/audits/2026-10-13-v1.5-*.md`, `docs/design/project-state.md`) use that name.

Blind-evaluated as a baseline audit and two audits of changes on a held-out application, with recorded owner decisions (`docs/audits/2026-10-13-v1.5-sequence-evaluation.md`).

- **Added after the self-audit, which does not cover them** (watch mode was also checked by the owner in a live Claude Code session: the check after an edit, the note at the end of a reply, and the session-start note all worked):
  - **Legal questions, at the right moment.** After an audit and in status, Flight Check says in plain English how many questions are worth asking a lawyer about and offers once to prepare the packet; legal questions do not block a release unless an answer says something must change. `/flight-check:legal-packet` (which Claude may now start when the user agrees) first lets the user sort each new question: ask a lawyer, their own decision, not relevant, or later. Each record is confirmed by the user. It builds one packet per release with every question for the lawyer. Watch mode reminds the user of questions waiting to be sorted or waiting for the lawyer's answer.
  - **Lighter on usage.**
    - After the first audit, `/flight-check:audit` re-checks only what changed (`--full` checks everything). It reuses the last inventory when no file was added or deleted and no dependency, build, or deployment file changed.
    - `--quick` is a spot check of the security-critical areas: one pass, a reading budget, the verifier, and the evidence check. It records nothing and gives no release decision.
    - Audits ask first when their estimate is above a spending limit ($5 by default), offering cheaper options. The `settings` command, or asking Claude, changes the limit and the model tier.
    - Agents and the audit coordinator now run on the Sonnet-class model Flight Check's accuracy and costs were measured with, instead of whatever model the session uses, so a session on a pricier model no longer multiplies an audit's cost. `--models economy` (cheaper agents) and `--models thorough` (the most capable model) are optional. Neither has been measured yet, so their estimates are wide.
    - The audit keeps raw agent replies out of the conversation and saves them in batches. In the App D baseline, the coordinating conversation accounted for about 70% of the tokens re-read during an audit.
  - **Plain English, and Claude fixes what it can.** Status, the end of an audit, and the release guide now lead with what is wrong, why it matters, and what to do, with IDs and official decision names in parentheses. Every item says whether Claude can fix it or the user must act. New `/flight-check:fix` lists what Claude can fix, asks once, fixes, and records each fix for the next audit to confirm. `finalize` returns `gate_plain`, the decision in plain words.
  - **Watch mode.** `/flight-check:watch on` keeps Flight Check alongside development. The plugin now has hooks, and they do nothing unless watch mode is on for the project. After each edit, free instant checks catch secrets written into code, HTTPS certificate checks turned off, debug mode left on, and an unignored `.env`. When changes pile up in sensitive code, a suggestion of a quick paid check states its cost; it never starts one. At session start, a status with due reminders.
  - **Never stuck.** "Remind me later" records a local reminder (`later`) that watch mode and status bring back. Every answer ends with the next step and the ways to move on: fix now, later, accept the risk, or mark it not a real problem.
  - **Skills Claude may start:** `status` and `fix` (the lint keeps every other skill manual, and pins the hooks to Flight Check's own script).
  - **How to get to READY.** `/flight-check:status` and `report --view unblock` list everything between the latest decision and READY, most serious first, each with its next step. For dependency vulnerability status, it gives the scanner commands for the ecosystems found at the project root (npm, pnpm, Yarn, Python, Go, Rust, Ruby, PHP, .NET, or OSV-Scanner for any) and how to import the output.
  - **Re-check specific controls.** `/flight-check:audit --recheck ID,...` (`init-run --recheck`) works like `--changed` and also reassesses the domains of the named controls, so a control the last decision could not verify can be re-examined, with new evidence or context, at a fraction of a full audit's usage.
  - **SARIF export.** `sarif --root .` turns the findings that count against release into SARIF 2.1.0 for GitHub code scanning, from the committed ledger; `docs/usage.md` has a workflow that uploads it. Ledger entries now keep the line each finding points to (`start_line`).
  - **Usage estimate.** `init-run` returns a rough usage range (`estimate`), scaled by project size, the number of domain agents, and `--passes`, and the audit skill states it before any agent starts. It is calibrated on Flight Check's measured audits.
- **Release check for CI** (added after the self-audit, which does not cover it): `release-check --root .` passes only when the latest ship decision is READY FOR RELEASE (or READY WITH ACCEPTED RISKS with `--allow-accepted-risks`), no record changed after it, no acceptance it relied on has expired, and every file git tracks matches the files as that audit started. Each finalized audit records those files in `.flight-check/audited-files.json` (commit it with the other state files), read from git's index without running git. `--mode warn` reports without blocking. It needs no Claude, so a release or deploy workflow can depend on it; `docs/usage.md` has a ready-to-copy GitHub Actions workflow. It is a process control: anyone who can commit can also edit the records.
- **Changes from the release self-audit** (`docs/audits/2026-10-13-v1.5-self-audit.md`):
  - In a git worktree or submodule, `.git` is a file, and audits of changes treated it as an unexplained change and reassessed every domain. Change detection now skips `.git` and `.hg` files. A stored file-list entry under a path the scan skips is ignored, not reported as deleted.
  - The high-entropy secret rule no longer masks timestamps such as `20261013T050120Z`, so backup names in messages stay readable.
  - The README states the current version, and the CI scan notes describe the current CI installs, including the unpinned PDF utility.

- **Fixes from a review of all project-state code** (Phase 10): an adversarial review by seven reviewers, one per area, found 54 candidate defects. Each candidate was to be checked by three independent skeptics, but a usage limit stopped them after 20 (19 confirmed, 1 rejected). 53 of the 54 were fixed with regression tests. The most serious:
  - `state recover` followed file names from a journal, so a planted `.flight-check/pending/journal.json` could delete or overwrite files outside the state directory; it now accepts only Flight Check's own file names and refuses links.
  - Several paths could make the ship decision better than the evidence supports: an owner's "not applicable" override hid open findings in that domain; linking a risk to any finding hid the risk; a finding matched by judgment inherited an acceptance made for a milder one; register acceptances and false-positive marks recorded during a run changed that run's decision; Flight Check could move a user's record back to PROPOSED or a user-set legal item back to NEEDS_REVIEW. All now count or refuse as documented.
  - Change detection could miss changes: a file cited only by a profile fact counted as explained; carried-forward findings could drop out of the gate after a later sighting; a domain the owner now says applies was carried forward as not applicable; impact rules were case-sensitive; any directory named `build`, `coverage`, or `vendor` was skipped at every depth; `./` paths never matched.
  - Robustness: restore, import, export, locks, and backups (ID counters never go back, damaged backups give an error, a dangling lock link fails fast); profile facts no longer grow without bound; corrections survive an aspect dropping out; contradicted corrections are shown.
  - Compatibility with the release candidate: `ledger legal IMPLEMENTED` no longer blocks release, its commands keep their reason rules, packets from its runs show the right progress, and recording commands migrate a release-candidate project.
  - The pre-approved `packet` command no longer writes to arbitrary paths.
- **Audits of changes only, from the blind sequence** (Phase 10): a source-code change now reassesses application security, authentication, authorization, data protection, and privacy, not application security alone, and each agent an audit of changes launches reassesses all of its domains. In the third App D run, a changed route file left authorization carried forward while the agent that could check it was already running for its other domains.
- **Finding identity across audits** (Phase 10): the verifier now receives the findings recorded by earlier audits and names the earlier one that is the same problem (`recorded_id`), so a finding keeps its ID and history when an agent rewords its rule, title, or domain. In the first blind sequence of audits over time, at least 15 of 26 "new" findings in the second run were rewordings of findings marked not reproduced; word matching could not separate them from different bugs at the same place. Exact fingerprints still match first, a regression found this way is reported as possible, and the finding's history notes each such identification. Re-running that step with the change: 5 new and 6 not reproduced instead of 26 and 32, with 35 findings keeping their IDs; one identification joined two different routes with the same kind of flaw, and the verifier's rule now says explicitly that those are different problems.
- **Agent replies from background agents** (Phase 10): `save-reply` now reads an agent's transcript (the output file Claude Code keeps for a background agent) and saves the agent's final reply, and the audit and remediate skills save every reply that way when such a file exists instead of retyping it. In the first blind run of the sequence, two long replies could not be written by hand and the audit stopped before its ship decision.
- **Hardening** (Phase 9): file lists are stored compactly and may be up to 100 MB, so change detection keeps working on large repositories instead of widening every time; files over 50 MB are compared by size in stored evidence as well as in the file list, so their evidence no longer looks stale; finalize reports a held lock as an error instead of failing with a traceback; the status skill treats record text as data. New tests for tampered run scopes, malformed file lists, linked or corrupt manifests, and stopped scans. `docs/security-design.md` covers the project-state additions.
- **Status, reports, and decision checks** (Phase 8): new read-only `status` command and `/flight-check:status` skill, which answers questions about the project from its records and maps requests it cannot carry out to the right command. New `report --view` command with Markdown and JSON (`report_version` 1.0) views of the profile, registers, legal queue, finding history, evidence status, changes, and readiness; `--out` writes only under `.flight-check/reports/`. `init-run` now returns the assertions of accepted decisions and the owner's applicability overrides; the audit skill passes the assertions to the domain agents and uses the overrides when choosing agents. A finding that contradicts a decision names it in `decision_ids`; finalize links them and marks the decision `NEEDS_REVIEW`.
- **Audits of changes only** (Phase 7b): `/flight-check:audit --changed` (`init-run --changed`) reassesses only the domains that changes since the last finalized audit can affect and carries the others forward as `CARRIED_FORWARD` coverage, labelled "carried forward, not reassessed". Carried-forward controls keep their last state only while their cited files are unchanged, otherwise they become UNVERIFIED; carried-forward findings still count in the ship decision (`carried_forward_findings` in `audit.final.json`, and in the gate output). Finalize re-checks the scope against the files, so a domain affected by a change made during the run is not carried forward. `project.json` records each domain's latest coverage and last assessment; ledger entries keep the effective confidence and release-blocking flag; `init-run` stores the file list as the run starts and that becomes the next baseline.
- **Change detection and freshness** (Phase 7a): each finalized audit stores the hashes of the files every finding, control, and positive control cites, and a local list of all file hashes. New `changes` command: changed files, the conclusions they affect and whose evidence is now stale or missing, decisions to review, and the domains to reassess versus carry forward; unexplained changes, an incomplete file list, or no list widen reassessment to every applicable domain. Impact rules are in `references/impact-rules.json`. Positive controls get stable `PC-` IDs. New finding statuses set only by the user (`ledger mark`): UNDER_REVIEW, REMEDIATION_PLANNED, FALSE_POSITIVE, SUPERSEDED. Regressions record how they matched, and a match by file and wording alone is reported as a possible regression. The ship decision now also counts release-critical requirements not verified by evidence, legal items needing action, and open or accepted CRITICAL risks in the register.
- **Legal review queue** (Phase 6): legal and business questions are `LR-` items with their own statuses (`NEEDS_REVIEW`, `AWAITING_COUNSEL`, `AWAITING_BUSINESS_DECISION`, `REVIEWED`, `ACTION_REQUIRED`, `RESOLVED`, `NOT_APPLICABLE`). Findings with a legal or business classification other than INFORMATIONAL open an item automatically; a regression reopens a closed one. Only the user records reviewed, resolved, or not applicable, with a note. The ledger moves to schema 2.0: on the first state change, each finding's 1.0 legal status and history move into an item (backup first), and `ledger legal` maps the 1.0 status names. Packets can include items without a finding (`item_ids`), use the new statuses, and are never built empty; `legal list` and the packet skill say "no specific legal-review issue has been identified" when nothing is open. `legal_status` in `audit.final.json` now holds the item status.
- **Requirements, decisions, and risks** (Phase 5): `req`, `decision`, and `risk` commands with status rules (only you accept, decide, or accept a risk; Flight Check's suggestions start as proposed). Links between records are checked. A requirement linked to controls becomes VERIFIED only when an audit verifies those controls with checked evidence and its linked findings are fixed; a risk is mitigated when its linked findings are verified fixed and reopened when one regresses. Risk acceptance needs a complete record and never lowers severity. `decision assertions` lists what accepted decisions say the code should satisfy. Also fixed: Phase 3's history entries for finding-level `ledger` commands now record the status change.
- **Project profile and applicability** (Phase 4): each finalized audit records evidence-backed profile facts (with file hashes, never quotes) and a per-domain applicability classification in `project.json`. A domain marked not applicable without evidence of what was searched is now treated as uncertain and still assessed. New commands: `profile show|correct|declare` and `applicability show|override`. Corrections and declarations never erase observations; contradictions are flagged. An owner override can mark an uncertain, unassessed domain not applicable ("declared by the project owner") but never hides a domain the evidence shows applies.
- **Project State persistence** (Phase 3): `.flight-check/project.json` (identity), `registers.json`, and a hash-chained `history.jsonl` log, created by `state init` or automatically by the next finalized audit or `ledger` command (a release-candidate ledger is backed up and kept unchanged). Every state change holds one lock, is schema-checked, journaled for crash recovery, and logged. New `state` commands: `show`, `check`, `recover`, `backup`, `backups`, `restore`, `export`, `import`, `adopt`. Runs record the project ID, and finalize refuses a run started for another project; state copied to another place in the repository must be adopted before use. Symbolic links in the state directory are refused.
- **Design for Project State** (`docs/design/project-state.md`): storage layout, identity, profile, applicability, requirements, decisions, risks, legal review items, history log, freshness, finding lifecycle, readiness, recovery, and migration from the release candidate. The schema definitions for the new state files are added and tested; nothing uses them yet.

## [1.0.0-rc.1] — 2026-10-12 (pre-release)

Release candidate for 1.0; never published as a release. Development versions (0.1.0) were never published as releases. Blind-tested in Phase 5 (`docs/audits/2026-10-06-phase-5-blind-test.md`), on a held-out application in Phase 7 (`docs/audits/2026-10-12-phase-7-final-report.md`), and on a second held-out application for this release candidate (`docs/audits/2026-10-12-v1-release-evaluation.md`).

- Changes from the release self-audit:
  - **Security map first.** Domain agents read a project's own security documentation early, use it only as a map to the files and tests it names, and verify each control there. Documentation alone never verifies a control. `docs/security-design.md` now also covers AI data boundaries and ledger integrity.
  - **Ledger lock.** Commands that change the ledger hold a lock file from read to write, so two commands running at once cannot lose each other's updates.
- Renamed the project from Fairtide to **Flight Check**: plugin id `flight-check`, commands `/flight-check:*`, script `flight_check.py`, working directory `.flight-check/`, finding IDs `FC-0001` (existing ledger IDs `FT-` became `FC-` with the same numbers), packet title "FLIGHT CHECK — ATTORNEY REVIEW PACKET", and the CI secret `FLIGHT_CHECK_LEAK_DENYLIST`. Nothing had been released under the old names.
- Changes after the Phase 7 final report:
  - **Fewer masked file paths.** The high-entropy secret rule no longer masks paths and slugs (for example a long dated file name), which had made affected components unreadable. Tokens that mix letters and digits in longer parts are still masked.
  - **CI tool install locked.** The Claude Code CLI used for plugin validation in CI now installs with `npm ci` from `tools/ci-npm/package-lock.json`, which pins every package with its integrity hash.
  - **Docs.** Installing a specific version and rolling back (`docs/installation.md`), a release procedure (`docs/maintainers/releasing.md`), and a stated retention rule for run directories: they are kept until you delete them.
  - **Repeat passes.** `/flight-check:audit --passes 2` (or 3) runs each domain agent independently two or three times and combines the results: a control counts as VERIFIED when any pass verified it with evidence that matches the files, NOT_MET from any pass still stands, and the verifier merges repeated findings. Language-model audits vary from run to run; combining passes is meant to find more issues and steady the ship decision, at about proportional usage for the domain audits.
  - **Product-logic checks.** The payments agent lists what each paid entitlement lets users create or hold and checks that every way the entitlement ends cancels or revokes it, and reviews how recurring dates and amounts are computed (month ends, drift, double runs). The testing agent reports data-layer tests that run only against a substitute for the production database. The governance agent checks how the terms can be changed, and whether real-world activities the product arranges are addressed in the terms.
  - **Owner-only run directories.** Each run directory (and `.flight-check/runs/` when Flight Check creates it) is now mode 0700, so only your user account can read the raw agent replies; files the script writes were already 0600. `docs/security-design.md` maps each protection to its code and tests. The repository's `.gitignore` also excludes `.env` files.
  - **Severity rule.** A routine operation (a scheduled job, a retry, a re-run) that would charge, refund, or delete for many customers at once in error is now listed as CRITICAL.
  - **Terms.** The README states there are no separate terms of use beyond the Apache-2.0 license and its disclaimers. CONTRIBUTING.md states that contributions are under Apache-2.0 with a Developer Certificate of Origin sign-off.
  - **CI installs locked.** Test-only tools install from `tools/ci-requirements.txt`, with exact versions and sha256 hashes for the CI Python versions.
  - **Large agent replies.** When Claude Code saves an oversized agent reply to a file, the audit and remediate skills now run `flight_check.py save-reply`, which copies the reply's JSON exactly into the run directory instead of having the coordinating session retype it. In Phase 7, one run stopped before its ship decision for this reason; replaying its stored reply through `save-reply` now passes validation.
  - **Quotes escaped more than once.** The evidence check now undoes up to three layers of HTML escaping (for example `&amp;gt;`) before declaring a mismatch. Re-checking the affected Phase 7 run lowered its failed findings from 7 to 1, a genuine mismatch.
- Changes from the Phase 6 release audit: a quote that skips lines with `...` must contain at least 12 checkable characters, or it is reported as uncheckable instead of matching; the README links the blind-test record and explains that run directories can be deleted.
- Changes from the Phase 5 blind tests:
  - **Documents compared with each other.** The governance agent builds a table of what each policy and statement says (time limits, audience and ages, governing law, liability, data, rights) and reports each conflicting topic as its own finding. A conflict between two documents is separate from a conflict with the code.
  - **Product promise sweep.** Promises in the README, marketing, help, and in-app text are listed first and each is checked against the code.
  - **Outbound-call sweep.** The platform agent checks every outbound call site for a timeout and files missing ones under reliability; the application-security agent leaves timeouts to it unless there is a security impact.
  - **Handler review.** The inventory lists every entry-point file. When there are more than 12, the audit launches up to eight extra application-security agents that each read up to 10 handlers end to end. In the de-identified security sample, a single agent read 10 to 13 of 50 handlers and judged the rest from search hits, which missed real issues and flagged safe code. A reviewer's NOT_MET control outranks the main agent's VERIFIED, and a failed reviewer keeps the affected controls UNVERIFIED. The verifier's turn limit was raised for the larger number of findings.
  - **Enumerate, don't sample.** Every domain agent examines every item a check applies to and reports counts in its coverage note; the application-security agent searches for every dangerous sink and reads each hit. Turn limits for the application-security, governance, and platform agents were raised to allow this.
  - **Framework behavior is not assumed.** A finding that depends on a framework's default behavior must read that behavior or state the assumption and stay at LIKELY or below; the verifier never states an unobserved default as fact.
  - **Deliberately vulnerable code** (training apps, benchmarks) is audited as found: one finding per vulnerability class with every affected location, at the severity it would have if deployed, lowered only when the project documents and its configuration shows that the code is never deployed.
  - **Attorney Review Packet questions.** The packet request may choose and order a finding's audit questions to leave out repeats (never add or reword them); the packet notes how many were left out as repeats. A business-decision finding without questions now says that it is a business decision instead of "no questions were generated". Skills use `<ID>` placeholders in examples, so example IDs are not copied into output.
  - **Audit root paths.** Agents build every path from the audit root exactly as given, and the audit skill reuses `run_dir` and the root verbatim. Agents had dropped the last directory of the root, Claude Code refused those reads, and one run stalled before finalize.
  - **Legal review flag.** A finding with a legal or business classification always gets the matching human-review flag when the run is assembled. A missing flag is now a warning instead of a validation retry; the flag can only add review.
  - **Blind-test tooling.** The runner streams every event to a log, reports denied tool calls, and audits a copy placed at the top of its temporary directory. `owasp_subset.py` builds a balanced OWASP Benchmark sample for the security domains outside this repository, and `stability.py` summarizes repeated runs.
  - **Stable finding IDs when agents reword rule names.** The ledger matched findings by the agent's free-form rule name, so an unchanged issue could get a new ID in the next run, and its old ID was marked NOT_REPRODUCED. Matching now takes exact fingerprints first. Then, only when exactly one entry qualifies, it accepts the same rule and file, or the same domain, file, and quoted line with a similar rule name or title, or the same domain and file with a nearly identical title. Ledger entries store a hash of the quoted anchor line (`anchor_hash`).
  - **Blind-test scoring.** The scorer also reports evidence coverage (issues covered by any finding's evidence), so a finding that groups several locations is credited in a separate number while strict matching stays one-to-one. `owasp_subset.py --deidentify` builds a local copy of the benchmark sample without its identifying names, category paths and messages, or project and license comments (the license and a notice of the changes are kept beside it). The runner reports success only when the audit was finalized (a session that stops at a usage limit after creating its run directory used to count as a success). The scorer reports location-only matches separately and marks unlisted findings that overlap an already-detected issue as possible repeats, as a hint for the person adjudicating.
- Changes from the first self-audit (see `docs/audits/2026-10-04-self-audit.md`):
  - **Decisions only you make now always prompt.** Each skill pre-approves only the script subcommands it needs. `ledger accept`, `revoke`, `legal`, and `close` are never pre-approved, and the lint enforces this. The headless runner and the hardened-mode settings allow only the audit subcommands and deny the ledger commands.
  - **Acceptances count only from the next run.** An acceptance recorded after a run started does not count for that run's ship decision.
  - **Accepted CRITICAL findings still block release.** The decision stays BLOCKED — CRITICAL RISK; the acceptance is recorded and shown.
  - **HTML-escaped quotes.** The evidence check accepts quotes whose `<`, `>`, or `&` were HTML-escaped in transit, restores the file's text, and notes the decoding. The audit skill saves agent output as received.
  - **Output contract.** UNVERIFIED controls may include `how_to_verify`, which the report shows. Agents report one issue per finding.
  - **Attorney Review Packet PDF.** It declares its document language (optional `language` in the packet request) and displays its title. It is still untagged; the Markdown copy is the accessible version.
  - **Leak gate.** The private-name denylist and the fixture canaries now cover every committable file, not only the plugin. The lint notes when no canaries are configured.
  - **Documentation.** Where audited content goes (your model provider), measured usage of an audit and how to limit it, PDF accessibility, and where self-audit reports are published.
- Changes from the Phase 4 re-audit:
  - **Secret masking now covers JSON outputs.** Likely secrets are masked in all agent text when a run is assembled, so `audit.final.json` and the ledger never hold them, not only the rendered report and packet (previously the README claimed more than the code did).
  - **Full audits verify pending fixes.** Every full audit asks the verifier to check findings recorded as REMEDIATED; before, only a targeted re-audit could move them to VERIFIED.
  - **Authorization control wording.** `AUTHZ-SERVER-SIDE` now applies to projects that serve multiple users or principals. Tool permission settings are not authorization in this sense, which kept the control's applicability, and with it the ship decision, from changing between runs.
  - **Agent retries.** A retry after a validation error launches a new agent rather than trying to message the earlier one.
  - **Remediation checks always apply.** A verifier's explicit check of a recorded fix now updates the ledger even when the finding's domain was not assessed in that run; before, it was silently ignored.
  - **Agent contracts.** The inventory agent must quote a line for every file it cites, and the verifier's contract lists the allowed evidence kinds; both had caused validation retries.
