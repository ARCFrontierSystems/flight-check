# Flight Check 1.5 sequence evaluation, 2026-10-13

This record covers the blind evaluation of Flight Check 1.5's continuous-assessment features on a new held-out application: a baseline audit followed by audits of two later commits, with owner decisions recorded before the first audit. Following the blind-test protocol, it reports aggregates only: no fixture code, names, or answer-key contents.

## Held-out application and sequence

- **Fixture:** testbed-D, a server-rendered web application in a language not used by the earlier fixtures, written in a separate session that never saw Flight Check's development. Its answer key stayed with the owner until every run had finished.
- **Baseline:** 28 planted issues (23 must-find, 5 stretch; none CRITICAL), 9 secure decoys, and one domain that does not apply.
- **Commit 2:** fixes 5 issues, attempts but does not complete a fix for 1, touches the code of 1 more only cosmetically, and introduces 2 new issues. The owner's key lists 5 domains as affected and 13 as unaffected.
- **Commit 3:** reintroduces one fixed issue (a regression) and introduces 1 new issue that violates a recorded decision. The key lists 5 domains as affected and 13 as unaffected.
- **Owner decisions:** 4 decisions with 10 assertions, recorded with `decision add` before the baseline. Only the commit-3 issue violates one of them.
- **Configuration:** `/flight-check:audit --passes 2` for the baseline, then `/flight-check:audit --passes 2 --changed` for each commit, each starting from the project state the previous run left. No imported evidence.
- **Cost:** $32.46 in total, including one baseline attempt that stopped (see "Tool problems found") and a first commit-2 run made before the identity fix. Each completed run cost between $5.85 and $6.88.

## Detection

| Must-find recall, strict | 0.91 | 0.95 | 0.68 |
| Recall, location only | 1.00 | 1.00 | 0.96 |
| Recall, location only, counting carried-forward findings | — | — | 1.00 |
| Decoy false positives | 0 | 1 | 0 |
| Severity within tolerance | 0.96 | 0.96 | 0.89 |
| Legal classification correct | 5 of 6 | 7 of 7 | 5 of 8 |
| Ship decision | BLOCKED — INSUFFICIENT EVIDENCE in every run | | |

- The commit columns use a line tolerance of 15 instead of 5, because the commits move code within files that the key locates by baseline line numbers.
- **Strict recall falls at commit 3** for two reasons. Findings in carried-forward domains have no new evidence to match, so they count only through the carried-forward finding (last row). Several findings were also filed under a neighbouring domain. Every open issue was covered by a finding or a carried-forward finding.
- **The ship decision** was expected to be NOT READY — REMEDIATION REQUIRED. Flight Check blocks as insufficient evidence instead, because dependency vulnerability status cannot be established without imported scanner output. This is intended, and was the same for the 1.0 fixtures.
- **Scorer artifact, adjudicated:** in every run, one finding about the debug-page setting was matched to a neighbouring decoy and counted as a decoy false positive, while that issue was credited to another finding. It is a true positive, and the table counts it as one. The remaining decoy false positive in commit 2 treated an in-memory rate limiter as a weakness, which the decoy shows is adequate for this deployment.

## Continuous assessment

**Scope of audits of changes.** No domain the key lists as affected was ever carried forward.
- **Commit 2:** the audit widened to every domain, because a changed source file was cited by no stored conclusion and matched no impact rule. This is the intended fail-safe; it saved nothing.
- **Commit 3:** 14 domains were reassessed, including all 5 affected ones, and 4 were carried forward, all of them unaffected. 9 unaffected domains were reassessed anyway, which is conservative.

**Decisions.** The commit-3 violation was reported at the commit that introduced it, as a finding linked to the decision, and the decision moved to NEEDS_REVIEW. Of the 12 decision-and-run pairs, the other 11 were satisfied, and none was flagged.

**Finding lifecycle.**

| | Commit 2, before the identity fix | Commit 2, after | Commit 3 |
|---|---|---|---|
| Findings reported as new | 26 | 5 | 5 |
| Findings marked not reproduced | 32 | 6 | 10 |
| Findings identified with an earlier one by the verifier | — | 35 | 28 |

- **Fixed issues at commit 2:** 3 of the 5 were marked not reproduced. Flight Check never marks a finding fixed without a verified remediation. The other 2 kept their earlier findings open:
  - In one, the verifier identified a new ownership-check bug on another route of the same file with the fixed one. That was wrong, and it led to a stricter identity rule.
  - In the other, a partial fix left related data in the logs. Treating this as the same problem is debatable.
  - Before the identity fix, all 5 were marked not reproduced, but most unchanged findings were also reissued under new IDs.
- **New issues:** all 3 (2 at commit 2, 1 at commit 3) were reported in the run that introduced them.
- **The regression at commit 3** reopened its earlier finding. Its status went from not reproduced to open, with the history kept. It is not labelled a regression, because the earlier disappearance was never verified as a fix ("not seen is not fixed").
- **Carried-forward findings:** at commit 3, 6 open findings in carried-forward domains were carried into the ship decision.

## Tool problems found and fixed

1. **Agent replies from background agents.** The first baseline attempt stopped before its ship decision. Claude Code now keeps a background agent's reply in a transcript file, and the coordinating session could not write two long replies by hand. `save-reply` now reads those transcripts, and the skills save every reply that way. The baseline was then run again.
2. **Finding identity across audits.** Agents reword rules, titles, and sometimes domains from run to run. Word matching could not separate rewordings from different bugs at the same place: true pairs scored as low as 0.24 similarity, while two different bugs in one file scored 0.67. The verifier now names the earlier finding that is the same problem. Commit 2 was run again with this fix, and the table shows both runs.
3. **Scope of source changes.** At commit 3, a changed route file left authorization carried forward. A source change had mapped only to application security, and the agent that also covers authorization was launched for its other domains only. The key shows authorization was not affected here. Still, a source change now reassesses application security, authentication, authorization, data protection, and privacy, and every launched agent reassesses all its domains. This costs some of the savings measured above.

## Disclosure: a rule that may have been informed by the fixture

The AI rule in `references/impact-rules.json` contained the file-name pattern `*triage*`. It was added in the change-detection phase, after the owner had sent the decisions for this evaluation, which mention a triage model. It may therefore have been informed by fixture knowledge, which the project's rules forbid. It was removed after the evaluation. It did not change the result: the files it would have matched were already cited by recorded AI findings, which brought their domain into reassessment anyway.

## Limitations

- One application and one sequence. These are first measurements of the 1.5 features, not a benchmark.
- Identity across audits is a model judgment: 1 of 35 identifications in the commit-2 rerun was wrong. Every identification is recorded in the finding's history, and a regression found this way is reported as possible.
- The commit-2 rerun and commit 3 used the identity fix; the baseline and the first commit-2 run did not.
- Under the protocol, App D is now spent: nothing learned from it may be presented as a held-out result again.
